<Aside type="caution" title="This is not a sandbox">
The flags on this page limit what Terragrunt does when a tool asks it to. They do not contain the programs Terragrunt
starts, and they do not stop an agent that can run shell commands from running `terragrunt run --all apply` itself,
with whatever credentials it can reach.

- A running `tofu` reaches the network whether or not `--allow=http` was granted. With `exec` granted and `http`
  denied, a `tofu init` still downloads providers from the registry.

- An `--allow-cmd` pattern bounds the arguments a command runs with, not what the program does with them.

- Under `--allow=env`, any environment variable the server has can come back in a tool result.

Give the server credentials scoped to what you are willing to have an agent reach, and point it at the smallest
directory that holds the units it needs.
</Aside>

## Tools

| Name            | What it does                                                                 | Needs                                                  |
| --------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------ |
| `discover`      | Lists the units and stacks under a directory                                 | None                                                   |
| `render_config` | Evaluates one unit's `terragrunt.hcl` and returns the resolved configuration | `exec` to read dependency outputs                      |
| `validate`      | Reports syntax and evaluation errors in the configurations under a directory | None                                                   |
| `run_order`     | Reports the order units run in, and what blocks each one                     | None                                                   |
| `get_outputs`   | Reads the applied outputs of one unit                                        | `exec`, or `http` for `s3`, `gcs`, and `azurerm` state |
| `plan`          | Runs `run --all plan` across the units and returns the per-unit result       | `exec`                                                 |

Two more tools are served only under
[`--dangerously-allow-apply`](/reference/cli/commands/mcp#dangerously-allow-apply). They change real infrastructure.

| Name      | What it does                                                | Needs  |
| --------- | ----------------------------------------------------------- | ------ |
| `apply`   | Runs `run --all apply` across the units                     | `exec` |
| `destroy` | Runs `run --all destroy` across the units, dependents first | `exec` |

Neither acts when the agent calls it. Each first returns an elicitation (the protocol's way for a server to ask the
client's user a question) naming the units it would run, and runs only once the person operating the client accepts.
A client that cannot ask anyone is rejected.

[`--working-dir`](/reference/cli/global-flags/#working-dir) sets the server root, and defaults to the directory the
server is launched in. Every tool takes a `working_dir` relative to the root. A value resolving outside it is refused,
symlinks included, and a filter following dependencies or dependents cannot return a unit from outside it.
`working_dir` is optional and defaults to the root, except on `render_config` and `get_outputs`, which act on a single
unit and require it. Where a tool takes `filter`, it accepts [filter queries](/features/filter) and narrows that tool
the way `--filter` narrows a run.

The root does not limit file access. `file()` reads anything the server's user can read, and resolving a dependency
downloads its source into a `.terragrunt-cache`.

The tools that run OpenTofu/Terraform use the binary the server was started with. Set it with
[`--tf-path`](/reference/cli/commands/mcp#tf-path), as a program name found in `PATH` or as a filepath. It defaults to
`tofu`, or to `terraform` when `tofu` is not installed. A unit's `terraform_binary` and `engine` block are ignored.

### discover

Lists the units and stacks under a directory.

- `filter` narrows what is returned.
- `dependencies` adds each unit's dependency edges, and whether an `exclude` block excluded it.
- `as` is the command those `exclude` blocks are evaluated against: `plan` (the default), `apply`, or `destroy`.
- `hidden` includes units in hidden directories.

Units and stacks come back as separate lists of paths, with `unit_count`.

### render_config

Evaluates one unit's `terragrunt.hcl` the way a run would, resolving locals, includes, functions, and dependency
outputs.

- `format` chooses how much comes back:
  - `summary`, the default, returns the unit's source, its remote state backend, the IAM role it assumes, the names of
  its inputs, its dependencies, and its generate blocks.
  - `full` returns the whole resolved configuration.
- `render_metadata` tags each value in a `format=full` result with where it was defined, so you can see which `include`
a value came from.

Without `--allow=exec`, dependency outputs fall back to `mock_outputs` where the configuration declares them, and the
call fails where it does not.

### validate

Checks the configurations under a directory for syntax and evaluation errors. Each diagnostic gives a `file`, `line`,
`severity`, `summary`, and `detail`. The result also counts errors and warnings, and sets `valid`.

- `unit` validates a single unit or stack, relative to `working_dir`. Discovery is skipped, and `filter` must be empty.
- `filter` narrows which units are validated.

### run_order

Reports the order units run in, based on the [DAG](/getting-started/terminology/#directed-acyclic-graph-dag). Each unit
lists the units that block it in `blocked_by`.

- `command` is the command the order is for: `plan` (the default), `apply`, or `destroy`.

- `format` selects the shape. `edges`, the default, returns the blocking relation as data. `tree` and `dot` return the
  graph as [`list`](/reference/cli/commands/list) prints it.

- `filter` narrows the set of units.

The `units` array is sorted by path.

### get_outputs

Reads one unit's applied outputs, what a `dependency` block on that unit receives.

- `include_sensitive` returns the values of outputs marked sensitive, which are otherwise replaced with `(sensitive)`.
  The agent sets it itself, and nobody is asked.

Each output comes back with its value and whether it is sensitive. `redacted` lists the names whose values were
replaced.

Under `--allow=exec`, Terragrunt runs OpenTofu/Terraform to read the outputs. Without it, Terragrunt reads the state
itself, which needs `--allow=http` and works for the `s3`, `gcs`, and `azurerm` backends. Any other unit reports that
it fetched nothing, and says why.

### plan

Runs `run --all plan` across the units under a directory. Each unit comes back with its result, how long it took, and
the cause when it failed. The result also counts what succeeded, failed, was excluded, and exited early.

- `filter` narrows which units are planned.
- `parallelism` caps how many units run at once, the way `--parallelism` does. By default there is no limit.
- `include_sensitive` keeps each unit's plan files and returns `plan_json`. The plan JSON holds every value in the plan
  in cleartext, sensitive ones included. Without it, Terragrunt deletes the plan files once it has counted their
  changes. The agent sets it itself, and nobody is asked.

Each unit result can have these fields:

| Field              | What it holds                                                                                                                                                                                                | Returned by                |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| `changes`          | Counts of resources the plan would add, change, destroy, import, and forget, and of outputs that would change. A plan that changes only outputs counts them under `outputs`.                                 | `plan`                     |
| `plan_json`        | Path of the plan's JSON representation, the document `tofu show -json` prints for the plan file. It contains every value in the plan, sensitive ones included. Only with `include_sensitive`.               | `plan`                     |
| `stdout`           | Path of a file with what OpenTofu/Terraform printed to stdout, color codes stripped, including the output of an `init` Terragrunt ran first. Sensitive values are redacted as the CLI redacts them.          | `plan`, `apply`, `destroy` |
| `stdout_truncated` | `true` when the file keeps only the last 8 MiB of the unit's stdout.                                                                                                                                         | `plan`, `apply`, `destroy` |

A unit that printed nothing has no `stdout`, and a unit whose plan failed has no `changes` or `plan_json`.

The files go in a directory under the system temp directory, readable only by the server's user, and are deleted when
the server stops.

### apply and destroy

Run `run --all apply` and `run --all destroy` across the units under a directory, destroy with dependents first. Both
answer in the shape `plan` does, with `stdout` and `stdout_truncated` and without `changes` or `plan_json`. An apply's
stdout has the apply summary and the unit's outputs, sensitive values redacted.

- `filter` narrows which units run.
- `parallelism` works as it does for `plan`.
- The approval prompt shows `filter` and `parallelism` as flags on the command it asks about.

## Connecting a client

Clients read a `.mcp.json` like the examples above. Set `TG_EXPERIMENT` in its `env`, since there is no shell to export
it from. Each client decides where the file lives and how much of this shape it reads, so check its own documentation:

- [VS Code](https://code.visualstudio.com/docs/agent-customization/mcp-servers)
- [Cursor](https://cursor.com/docs/mcp)
- [Claude Code](https://code.claude.com/docs/en/mcp)

## Capabilities

The server denies every capability at startup, and grants each one separately:

| Flag                                                                                | What it allows                                                   |
| ----------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| [`--allow`](/reference/cli/commands/mcp#allow)                                      | Any of `exec`, `http`, `sops`, or `env`. Repeat it for each one. |
| [`--allow-cmd`](/reference/cli/commands/mcp#allow-cmd)                              | A command pattern a configuration may run                        |
| [`--dangerously-allow-apply`](/reference/cli/commands/mcp#dangerously-allow-apply)  | The `apply` and `destroy` tools                                  |

Wherever a denied capability stops a tool, the result includes a `degraded` list naming what it did instead, such as
substituting `mock_outputs` for a dependency output.

### exec

Lets the tools run the `tofu`, `terraform`, and `git` that Terragrunt starts for its own work: a plan, a source
download, a git-range filter. It does not let a configuration run those programs itself. A program a configuration
names, through `run_cmd()`, a hook, or `--auth-provider-cmd`, is refused like any other.

A refused program is reported in the call's `degraded` list and the call continues, with `run_cmd()` yielding an empty
string. `apply` and `destroy` fail the unit instead, so a hook written to block the run still blocks it.

To run a program a configuration names, allow it with an [`--allow-cmd`](/reference/cli/commands/mcp#allow-cmd)
pattern, or accept it when a tool asks. A pattern naming `git` matches the `git` on the server's `PATH`, not a `./git`
in the tree.

`discover`, `render_config`, `validate`, and `run_order` ask. When a configuration names a refused program, the call
returns an elicitation naming the programs, then runs again with the ones the person operating the client accepts. An
acceptance covers those programs for that call only. `get_outputs`, `plan`, `apply`, and `destroy` never ask.

### http

Covers what Terragrunt itself fetches:

- Downloading a unit's `terraform { source }` when it is remote, such as a `tfr://` registry module, an `https`
archive, or an `oci://` image. Without this, such a unit cannot be planned.

- Fetching a stack's sources during discovery and generation.

- Reading remote state directly for `get_outputs`.

- Cloud API calls Terragrunt makes itself, including assuming a role through STS and reading S3, GCS, or Azure Storage.

- Provider downloads made by the provider cache server.

### sops

Without it, a configuration calling `sops_decrypt_file` fails, so a unit whose inputs come from an encrypted file
cannot be rendered. A refused decrypt fails the call. No value is substituted.

<Aside type="caution" title="Granting sops shows the agent your secrets">
Decrypted values flow into whatever the tool returns. `render_config` with `format=full` puts resolved inputs in
the result, so a secret read through `sops_decrypt_file` reaches the model, and from there whatever your client logs
or sends onward.
</Aside>

### env

Without it, a tool call starts from an empty environment. A configuration's `get_env()` returns its default, and every
command the tools run, `tofu` included, sees none of the server's variables. Terragrunt still finds `tofu` and `git` on
the server's own `PATH`.

Granting it passes every one of the server's environment variables to configurations and the commands the tools run, as
every other Terragrunt command does. That can include cloud credentials.

Without it, the server also points `HOME` at an empty directory, so nothing reads `~/.aws/credentials`,
`~/.gitconfig`, or an age key file. A direct state read under `http` and a decrypt under `sops` both need `env` to find
credentials in the environment or your home directory.

## Logs

Logs, and any output from the commands the tools run, go to standard error, where MCP clients typically surface them
as server logs. Standard output carries the protocol itself.
