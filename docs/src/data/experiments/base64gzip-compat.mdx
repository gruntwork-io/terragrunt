Support for the `base64gzip_compat` HCL function.

This experiment flag is no longer needed, as `base64gzip_compat` is available by default.

### `base64gzip-compat` - What it does

Terragrunt exposes a `base64gzip_compat(str)` HCL function that returns the value `base64gzip(str)` returned in Terragrunt v1.1.3 and earlier, and keeps returning it now that Terragrunt 1.2 has switched `base64gzip()` to the current Go encoder.

Use it where the encoded value must stay stable across upgrades, such as an EC2 instance with `user_data_base64` and `user_data_replace_on_change = true`.

### `base64gzip-compat` - How to provide feedback

Now that the `base64gzip-compat` experiment is complete, please provide feedback in the form of standard [GitHub issues](https://github.com/gruntwork-io/terragrunt/issues).

### `base64gzip-compat` - Criteria for stabilization

To transition the `base64gzip-compat` feature to a stable release, the following were addressed:

- [x] Settle the function name with OpenTofu. OpenTofu chose not to add a compatibility function, opting for a temporary warning diagnostic instead ([opentofu/opentofu#4578](https://github.com/opentofu/opentofu/issues/4578)), so there is no counterpart name to match and `base64gzip_compat` stays Terragrunt-specific.
- [x] Confirm the output stays byte-identical across Terragrunt and Go releases. The encoder writes its own gzip framing and compresses through a vendored copy of `compress/flate`, so a Go toolchain upgrade cannot move the bytes, and golden vectors pin the output.
