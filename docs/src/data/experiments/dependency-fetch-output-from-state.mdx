Support for fetching dependency outputs directly from state files.

### `dependency-fetch-output-from-state` - What it does
By default, Terragrunt retrieves dependency outputs by running `tofu output` or `terraform output` commands, which requires initializing the dependency unit and can be slow. When this experiment is enabled, Terragrunt will attempt to fetch dependency outputs directly from the remote state file, bypassing the need to initialize the dependency and significantly speeding up dependency processing.

<Since version="1.2.0">
This experiment flag is no longer needed, as fetching dependency outputs from state is now the default. Disable it with the `--no-dependency-fetch-output-from-state` flag.

Reading state directly is an optimization and never decides whether a run succeeds. When a direct read fails for any reason other than the state not existing yet, Terragrunt retrieves the outputs through OpenTofu instead and the run continues. A dependency whose state does not exist yet still resolves to that dependency block's `mock_outputs`.
</Since>

**Current Backend Support:**

- S3 and GCS backends: Direct state reads are supported
- Azure Storage (`azurerm`) backend: Direct state reads are supported when the [`azure-backend`](/reference/experiments/active#azure-backend) experiment is also enabled
- Other backends: Falls back to the normal method (using `tofu/terraform output`)

Azure state protected with `customer_provided_key`, and Azure configurations that rely on native-only authentication, `metadata_host`, or `timeout_seconds`, also use the normal method.

GCS configurations that rely on backend-only credential environment variables, inline credentials or relative credential-file paths, the `impersonate_service_account` setting, custom storage endpoints, custom universe domains, or competing credential sources with different precedence also use the normal method. This preserves the native backend's authentication and endpoint behavior.

The `credentials` backend setting is a local path to a Google Cloud credentials file in JSON format. `GOOGLE_APPLICATION_CREDENTIALS` points to the same kind of file. Neither is the same thing as `access_token`, which is a temporary OAuth 2.0 access token used as-is rather than a file.

Terragrunt reads credentials files of type `service_account`, `authorized_user`, and `external_account` (Workload Identity Federation) directly. An `external_account` file is read directly only when its `credential_source` is a `url` or a `file` with an absolute path. Any other source uses the normal method, because a direct read would resolve it with Terragrunt's own environment and working directory rather than the unit's:

- `executable` would run the command with Terragrunt's environment.
- AWS (an `environment_id` such as `aws1`) would use Terragrunt's AWS credentials.
- `file` with a relative path would resolve against Terragrunt's working directory.

**Failure handling:**

<Before version="1.1.5">
Outside `render` and `render-json`, a network, permissions, or parsing failure from a direct state read ends the run instead of retrying through OpenTofu/Terraform. A missing state object still follows the dependency block's `mock_outputs` behavior.
</Before>

<Since version="1.1.5">
Reading state directly is an optimization. Outside `render` and `render-json`, Terragrunt retries a failed direct read with `tofu output` or `terraform output`, unless the state object is missing. If native output retrieval succeeds, only the speedup is lost. For missing outputs, Terragrunt uses configured `mock_outputs` only when they are allowed for the original command. `skip_outputs` skips output retrieval and returns eligible configured mocks. The render commands retain their tolerant behavior and can use configured mocks regardless of the command allow-list.
</Since>

**OpenTofu state encryption:**

<Before version="1.1.5">
This experiment is **not compatible with OpenTofu state encryption**. When OpenTofu's [client-side state encryption](https://opentofu.org/docs/language/state/encryption/) is enabled, the encrypted envelope carries no plaintext `outputs` object. Terragrunt treats the dependency as having no outputs. Referencing a missing output can then fail with `Unsupported attribute`, while configured mock-output merging can supply a mock value instead. Disable this experiment using `--no-dependency-fetch-output-from-state` to force native output retrieval.
</Before>

<Since version="1.1.5">
The direct reader cannot decrypt state protected by OpenTofu's [client-side state encryption](https://opentofu.org/docs/language/state/encryption/) because it does not evaluate OpenTofu's encryption configuration or key providers from the `remote_state.encryption` map. Outside `render` and `render-json`, Terragrunt recognizes the encrypted envelope and retries with `tofu output` or `terraform output`, allowing the configured binary to decrypt the state when it supports that encryption. If native output retrieval succeeds, only the speedup is lost. For missing outputs, Terragrunt uses configured `mock_outputs` only when they are allowed for the original command. `skip_outputs` skips output retrieval and returns eligible configured mocks. The render commands retain their tolerant behavior and can use configured mocks regardless of the command allow-list. Disable the experiment when a render command must resolve real outputs from encrypted state.
</Since>

**Disabling the feature:**

You can disable the dependency-fetch-output-from-state feature using the `--no-dependency-fetch-output-from-state` flag:

```bash
terragrunt run --all --no-dependency-fetch-output-from-state -- plan
```

### `dependency-fetch-output-from-state` - Criteria for stabilization
To transition the `dependency-fetch-output-from-state` feature to a stable release, the following were completed:

- [x] Add support for additional backends (GCS and Azure Storage)
- [x] Live direct-state-read integration coverage for S3, GCS, and Azure Storage
- [ ] Comprehensive integration testing across backend authentication, encryption, workspace, and error scenarios
- [ ] Performance benchmarking to validate speed improvements
- [x] Error handling and edge case testing
- [x] Documentation of supported backends and limitations
- [x] Handle OpenTofu state encryption gracefully (fallback or explicit error message)
- [ ] Community feedback on real-world usage
