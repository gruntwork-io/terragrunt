The `autoinclude` block goes inside a [`unit`](/reference/hcl/blocks/unit/) or [`stack`](/reference/hcl/blocks/stack/) block in a `terragrunt.stack.hcl` file. It declares dependencies between the components of a stack, and other configuration they need, without editing the unit sources in your catalog.

[`terragrunt stack generate`](/reference/cli/commands/stack/generate) writes the block's body to a file in the generated component's directory: `terragrunt.autoinclude.hcl` next to a unit's `terragrunt.hcl`, or `terragrunt.autoinclude.stack.hcl` next to a nested stack's `terragrunt.stack.hcl`. Terragrunt merges that file into the component's configuration whenever it parses the component.

The block takes no label and has no attributes of its own. In a `unit` block, its body can contain:

- `dependency` blocks. `config_path` usually reads a `unit.<name>.path` or `stack.<name>.path` variable, described [below](#component-path-variables). Every other attribute works as it does in a regular [`dependency`](/reference/hcl/blocks#dependency) block.
- The [`inputs`](/reference/hcl/attributes/inputs/) attribute.
- Any other block a unit configuration accepts, e.g. `feature`, `errors`, `generate`, or `remote_state`.

Terragrunt rejects:

- A `locals` block. Declare locals in `terragrunt.stack.hcl` instead.
- The `values` attribute, which a unit configuration doesn't accept. Set `values` on the `unit` block instead.
- An `autoinclude` block.

Expressions in the body resolve when Terragrunt generates the stack, in the context of the stack file. `local.*`, `values.*`, `unit.<name>.path`, `stack.<name>.path`, and function calls become literal values in the generated file. Functions run as if called from the stack file, so `get_terragrunt_dir()` returns the stack file's directory and `path_relative_to_include()` returns `"."`. Terragrunt keeps `dependency.*` references as written, since dependency outputs exist only when the unit runs.

### With `expansion`

When the `unit` or `stack` block has an [`expansion`](/reference/hcl/blocks/expansion/) block, Terragrunt writes a file for each instance, and `each.key`, `each.value`, and `count.index` in the `autoinclude` body resolve to that instance.

A `dependency` block in the body can have its own `expansion` block. Terragrunt evaluates its `for_each` or `count` in the stack file's context and writes the result into the generated `expansion` block as a literal value. It resolves `config_path` once per instance and writes it as a lookup by `each.key` or `count.index`. Other `each.*` and `count.index` references in the dependency block stay as written, and the generated unit expands the dependency again when Terragrunt parses it:

```hcl
# terragrunt.stack.hcl

locals {
  regions = toset(["us-east-1", "us-west-1"])
}

unit "vpc" {
  expansion {
    for_each = local.regions
  }

  source = "../catalog/units/vpc"
  path   = "vpc/${each.key}"

  values = {
    region = each.key
  }
}

unit "app" {
  source = "../catalog/units/app"
  path   = "app"

  autoinclude {
    dependency "vpc" {
      expansion {
        for_each = local.regions
      }

      config_path  = unit.vpc[each.key].path
      mock_outputs = { vpc_id = "vpc-mock-${each.key}" }
    }

    inputs = {
      vpc_ids = {
        for region, vpc in dependency.vpc : region => vpc.outputs.vpc_id
      }
    }
  }
}
```

```hcl
# .terragrunt-stack/app/terragrunt.autoinclude.hcl

# Generated by Terragrunt from an autoinclude block. Do not edit manually.
dependency "vpc" {
  expansion {
    for_each = toset(["us-east-1", "us-west-1"])
  }

  config_path = {
    us-east-1 = "../vpc/us-east-1"
    us-west-1 = "../vpc/us-west-1"
  }[each.key]
  mock_outputs = { vpc_id = "vpc-mock-${each.key}" }
}

inputs = {
  vpc_ids = {
    for region, vpc in dependency.vpc : region => vpc.outputs.vpc_id
  }
}
```

When the `unit` block and the `dependency` block are both expanded, the dependency's `for_each` or `count` reads the unit's instance. Everywhere else in the dependency block, `each` and `count` refer to the dependency's own instance.

### Component path variables

A `terragrunt.stack.hcl` file has a `unit.<name>.path` or `stack.<name>.path` variable for each `unit` and `stack` block it declares. Each one is the component's generated directory, including the effect of `no_dot_terragrunt_stack`. In a generated dependency, Terragrunt writes `config_path` relative to the unit's directory.

`autoinclude` blocks and the `values` attribute of `unit` and `stack` blocks can read these variables, so a stack can pass a component's path down to a nested stack. Only components declared in the same stack file are visible, and referring to an undeclared name fails generation.

An [expanded](/reference/hcl/blocks/expansion/) component has a path for each instance, under the key its [address](/reference/hcl/blocks/expansion#addressing-expanded-units-in-stack-output) uses: `unit.vpc["us-east-1"].path` for a `for_each`, or `unit.shard[0].path` for a `count`.

### Merge behavior

Terragrunt merges `terragrunt.autoinclude.hcl` into the unit's configuration as it does a regular [`include`](/reference/hcl/blocks#include) with the default strategy: a shallow merge in which the autoinclude wins. Top-level keys from both files combine. When both set a key, the autoinclude's value replaces the unit's, without merging nested maps. `inputs` maps combine key by key. A `dependency` block with the same name as one in the unit's `terragrunt.hcl` replaces it.

Terragrunt merges a `terragrunt.autoinclude.hcl` file next to any unit's `terragrunt.hcl`. `stack generate` writes and overwrites it, so don't edit it by hand.

### Depending on a sibling stack

A dependency's `config_path` can read `stack.<name>.path` to depend on a nested stack. The dependency's outputs then include every unit the stack generates, keyed by unit and nested stack name, as described in [Depending on a stack](/reference/hcl/blocks#depending-on-a-stack).

```hcl
# terragrunt.stack.hcl

stack "network" {
  source = "../catalog/stacks/network"
  path   = "network"
}

unit "app" {
  source = "../catalog/units/app"
  path   = "app"

  autoinclude {
    dependency "network" {
      config_path = stack.network.path

      mock_outputs_allowed_terraform_commands = ["validate", "plan"]
      mock_outputs = {
        vpc = {
          vpc_id = "mock-vpc"
        }
      }
    }

    inputs = {
      vpc_id = dependency.network.outputs.vpc.vpc_id
    }
  }
}
```

The `network` stack contains a unit named `vpc` with a `vpc_id` output, so `app` reads it as `dependency.network.outputs.vpc.vpc_id`.

### Stack-level autoinclude

In a `stack` block, the `autoinclude` body can contain only `unit` and `stack` blocks. Terragrunt writes them to `terragrunt.autoinclude.stack.hcl`, next to the nested stack's `terragrunt.stack.hcl`, and adds them to that stack. A block with the same name as a `unit` or `stack` block in the nested stack replaces it, including its `path` and `autoinclude`.

```hcl
# terragrunt.stack.hcl

stack "networking" {
  source = "../catalog/stacks/networking"
  path   = "networking"

  autoinclude {
    unit "extra" {
      source = "${get_repo_root()}/catalog/units/extra"
      path   = "extra"
    }
  }
}
```

Terragrunt rejects a `dependency` block here, because a stack has no dependencies of its own. Declare it in the `autoinclude` block of the unit that needs it.

### Limitations

- `unit.<name>.path` and `stack.<name>.path` only see components declared in the same stack file, so an `autoinclude` block can't refer to a unit inside a nested stack. Depend on the whole stack, or pass the component's path down to the nested stack through `values`.
- A `unit` or `stack` block added by a stack-level `autoinclude` can have its own `autoinclude` block. Terragrunt resolves it in the next generation pass, and its `unit.<name>.path` and `stack.<name>.path` references resolve in the stack file that declares it.
- Only HCL stack files support `autoinclude`. A JSON stack file that declares one fails generation.
